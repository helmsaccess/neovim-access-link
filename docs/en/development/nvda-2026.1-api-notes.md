# NVDA 2026.1.1 API review

Reviewed source: official tag `release-2026.1.1`, commit
`5d92106f17e461dac62aa48257bbbf4183e033d0`.

Confirmed points include 64-bit Python 3.13.12, GlobalPlugin/AppModule script
and event behavior, event-queue handoff through `queueHandler`, diff-based and
UIA-notification Windows Terminal paths, typed-character handling, validated
manifest API versions, settings category registration, and configuration
profile callbacks.

The official developer guide documents `inputCore.decide_handleRawKey` as a
public `Decider`, but it is too early for this observer: returning `True` only
permits further NVDA processing. The AppModule instead observes F12 through
the public `inputCore.decide_executeGesture` decider and returns `True` without
binding a script. NVDA then raises `NoInputGestureAction`, causing the keyboard
hook to pass the original physical event to the OS. Claim work is queued
separately and never runs on the input-hook thread. Only after an F12 match does
the decider query `api.getFocusObject()`; it accepts only that concrete,
still-registered AppModule instance and the same complete terminal identity in
the gate.
Neovim's corresponding `vim.on_key` observer likewise schedules its session-file
write with `vim.schedule()` rather than invoking regular Vim functions from
the key callback. Neovim 0.11 adds the public return contract which lets a
callback consume a key by returning `""`; Neovim 0.10 does not yet have that
contract.

`braille.handler.handleGainFocus` rebuilds the ordinary focus/main buffer but
does not display it while NVDA's Braille message buffer is active. The public
`braille.handler.message` path is appropriate for a spelling suggestion that
must change immediately: it uses NVDA's selected translation, switches the
visible buffer, and updates the physical display. NVDA itself uses this path
for suggestion and selection feedback. NVDA 2026.1.1 has no public operation
to dismiss exactly one owned Braille message immediately and no per-message
lifetime argument. The narrowly guarded, identity-checked use of
`messageBuffer`, the visible `buffer`, `regions`, the message timer, and
`_dismissMessage` is therefore documented in
[ADR-0002](adr/0002-nvda-api-boundaries.md).

The public horizontal scroll command calls `Region.nextLine()` at a boundary,
and the line command calls that region method directly. A custom
`braille.Region` installed only in the proven message buffer can therefore
constrain long developer information to local pages. Because NVDA restarts
the general message timer after horizontal scrolling, the region stops it
again after the command and only after repeating the same ownership check.

The public `braille.Region` base class translates `rawText` with `cursorPos`
and exposes `brailleToRawPos` for `routeTo`. It retains a final blank, allowing
the structured Insert and command-line plans to expose a virtual end cell
without private Braille APIs. Documented `selectionStart` and `selectionEnd`
raw-text positions are marked by `Region.update()` with NVDA's fixed dots 7
and 8 when `braille.showSelection` is enabled. Focus and review cursor shapes
remain separately controlled by NVDA.

Public
[`braille.TextInfoRegion`](https://github.com/nvaccess/nvda/blob/5d92106f17e461dac62aa48257bbbf4183e033d0/source/braille.py#L1327-L1340)
marks regions that participate in normal caret following. Public
[`braille.handler.handleCaretMove`](https://github.com/nvaccess/nvda/blob/5d92106f17e461dac62aa48257bbbf4183e033d0/source/braille.py#L3116-L3136)
marks the focus region for an update; NVDA then restores the previous viewport
and calls
[`scrollToCursorOrSelection`](https://github.com/nvaccess/nvda/blob/5d92106f17e461dac62aa48257bbbf4183e033d0/source/braille.py#L3176-L3184)
only when the cursor is outside it. The structured region therefore derives
from `TextInfoRegion`, but translates its semantic Neovim text through public
`Region.update()` rather than an NVDA `TextInfo`. Insert, Normal, and
command-line modes thereby follow NVDA's standard behavior without reading
private buffer or scroll fields.

`braille.Region` exposes the public `nextLine()` and
`previousLine(start=False)` extension points. NVDA's global commands for
moving a Braille display to the previous or next line call these methods on
the final region. The add-on overrides exactly these methods and registers no
display-specific gestures. The
[Papenmeier driver at the examined tag](https://github.com/nvaccess/nvda/blob/5d92106f17e461dac62aa48257bbbf4183e033d0/source/brailleDisplayDrivers/papenmeier.py#L452-L457)
maps `left`, `right`, `up`, and `dn` to NVDA's standard commands; the
[NVDA user guide](https://download.nvaccess.org/releases/2026.1/documentation/en/userGuide.html)
documents the same assignment and lists the BRAILLEX EL 80c as supported.

The Braille cursor/exploration toggle is an ordinary freely assignable
AppModule script. Both modes continue to use the same public region methods;
strategy selection remains behind the add-on's service boundary. It reads no
driver objects or private gesture, Braille-buffer, or scroll-position state.

Repeated routing uses NVDA's public, profile-aware
`config.conf["keyboard"]["multiPressTimeout"]` setting. NVDA's own
[script handler](https://github.com/nvaccess/nvda/blob/5d92106f17e461dac62aa48257bbbf4183e033d0/source/scriptHandler.py#L294-L315)
uses the same value, whose 100 through 20,000 ms limits are defined by the
[configuration schema](https://github.com/nvaccess/nvda/blob/5d92106f17e461dac62aa48257bbbf4183e033d0/source/config/configSpec.py#L193).
Deferred local resolution uses NVDA's public main-loop function
[`core.callLater`](https://github.com/nvaccess/nvda/blob/5d92106f17e461dac62aa48257bbbf4183e033d0/source/core.py#L1182-L1183).
No private gesture counter or timer internals are read.

Horizontal panning remains entirely in NVDA's public Braille buffer. At the
start or end of the translated buffer, its standard behavior also calls
`previousLine()` or `nextLine()`. `previousLine(start=True)` already
distinguishes NVDA's direct up command from backward panning with the default
`False`. `nextLine()` has no corresponding parameter. The Windows Terminal
AppModule therefore observes only the global `braille_nextLine` command
confirmed through `scriptHandler.getScriptName()` and `getScriptLocation()`
at the public
[`inputCore.decide_executeGesture` extension point](https://github.com/nvaccess/nvda/blob/5d92106f17e461dac62aa48257bbbf4183e033d0/source/inputCore.py#L474-L486).
A marker bound to the exact focus object, AppModule, adapter token, and service
generation expires through `queueHandler.eventQueue` after the same input
turn. It neither changes nor blocks the gesture. Direct down navigation thus
retains the column, while right beyond line end starts at the next line's
beginning. The structured region accesses no driver objects or private buffer
or script state.

When focus leaves an active Braille exploration session, the add-on reads the
public `BrailleBuffer.windowStartPos` property before NVDA rebuilds the focus
buffer. That integer is stored with the Neovim buffer, window, and tab
identity in the session runtime. After `handleGainFocus` rebuilds the same
structured region, the validated and length-clamped value is assigned through
the same public property and `BrailleHandler.update()` displays it. Review
tether, message buffers, another region type, and a changed Neovim context
all prevent restoration.

`braille.getFocusRegions()` explicitly treats `AttributeError` and
`NotImplementedError` from `getBrailleRegions()` as a request for native
fallback. The structured overlay uses exactly that contract for review tether.
For focus tether, public `handleGainFocus(..., shouldAutoTether=False)` and
`handleUpdate()` provide rebuild and incremental update paths. A region with a
cursor but no cells cannot be focused by `BrailleBuffer.focus()`, so an empty
Normal-mode editor line exposes one virtual blank and sets public
`hidePreviousRegions` to replace preceding terminal focus context.

The official English UI strings confirm these paths:

- `NVDA menu → Preferences → Settings...`
- `NVDA menu → Preferences → Input gestures...`
- `NVDA menu → Tools`
- `NVDA menu → Configuration profiles...`

Suppression may skip downstream handling only for an active, authenticated,
focused, exactly bound Neovim session. Timeout, exception, focus loss,
termination, or deactivation must restore normal handling.

Windows Terminal controls across tabs/windows and scripts were tested with NVDA 2026.1.1;
other front ends and broader NVDA/UIA versions remain unapproved.
